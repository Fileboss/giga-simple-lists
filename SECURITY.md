# Security

This document explains the app's security choices and the reasons behind them. How things work in
detail is in the [README](README.md) ("Design notes") and in the code.
[Version française](SECURITY.fr.md).

## Reporting a vulnerability

No public issue, please: use *Security → Report a vulnerability* on the repository's GitHub page
(private report). Include the version (tag or image) and the steps to reproduce.

## Threat model

The app is meant to be **exposed to the Internet**: bots will try to sign in from day one. It holds
grocery and to-do lists, **not sensitive data**.

Hence the priority: **a flaw in the app must lead nowhere.** Not to the host, not to the local
network, not to the other services running next to it. The confidentiality of the lists comes
second.

## Decisions

### Password-only sign-in

- **No second factor** (TOTP, passkeys). An early version asked for a TOTP code at every sign-in:
  too much friction for grocery lists, for little gain. The password generated by `listes user add`
  is 24 characters long (about 120 bits), impossible to guess, and attempts are rate-limited.
- **Argon2id**, OWASP parameters (m = 19 MiB, t = 2, p = 1), at most 2 concurrent computations to
  stay within the container's memory limit.
- **Same message and same duration** (at least 800 ms) for every refused sign-in: unknown account,
  wrong password, blocked IP. Nobody can find out which accounts exist.
- **No online sign-up, no "forgot password" e-mail, no web administration**: accounts are managed
  from the command line only. Less attack surface, and nothing to steal through e-mail.

### Rate limiting

- **Per IP: blocking.** Beyond 10 failures in 24 h, the IP is blocked for 30 s, then 1 min,
  2 min… up to 1 h.
- **Per account: slowdown only**, capped at 1 min (at most 32 slowed-down attempts waiting). A real
  per-account lockout would let anyone who knows a name keep its owner from signing in.
- Counters are **stored in the database**: a restart does not reset them.

### Sessions

- 256-bit random token in the cookie; **only its SHA-256 is stored**: a copy of the database gives
  access to no session.
- `__Host-session` cookie: `Secure`, `HttpOnly`, `Path=/`, no domain.
- Exception, on explicit request only: `LISTES_INSECURE_HTTP=true` with an `http://` origin other
  than localhost (trying it on a local network). Browsers would reject a `Secure` or `__Host-`
  cookie received over HTTP, so the cookies become `listes_session` and `listes_login`, without
  `Secure`, and travel in clear text. Without the option, an `http://` origin other than localhost
  stops the app at startup, and the option is refused with an `https://` origin: an HTTPS instance
  cannot lose `Secure` by mistake. CSRF protection (Origin, Sec-Fetch-Site, token) is unchanged.
- **`SameSite=Lax`, not `Strict`.** Opened from the home screen (iOS especially), the app starts
  with a navigation that the browser treats as coming from another site: a `Strict` cookie is not
  sent, and the app asked to sign in again every time. `Lax` only sends the cookie from another site
  on a GET navigation, and no GET route modifies data.
- 90 days without a visit, 180 days at most. A new session at every sign-in. Revocation from the
  command line (`user reset`, `sessions revoke-all`). The real-time stream re-checks the session
  every 20 s.

### Requests that modify data: three CSRF protections

`Origin` required and equal to `LISTES_ORIGIN`, `Sec-Fetch-Site` equal to `same-origin` when
present, and a per-session CSRF token. One would be enough in practice; the three together cover
old browsers and configuration mistakes.

### Access to lists

- **A single rule** (`visibleTo`: owner, or shared list) and **a single gate**
  (`accessList` / `accessItem`) for every route and for the real-time stream: no check rewritten
  route by route, so no route can forget it.
- Rights on an item come from its list, looked up server-side; a list identifier sent by the client
  is never trusted.
- Someone else's private list: **404**, not 403, so as not to reveal that it exists.
- **128-bit** identifiers, impossible to guess.

### Browser

- **Strict CSP, no inline script or style**, no external resource (no CDN, no font). Together with
  `html/template`'s automatic escaping, an injected script does not run.
- Headers set by the app: COOP, CORP, a `Permissions-Policy` that denies everything,
  `X-Frame-Options: DENY`, `Cache-Control: no-store` on signed-in pages. HSTS, `nosniff` and
  `Referrer-Policy` must be added by the reverse proxy (README).
- **Offline**: the service worker always goes to the network first, and only uses its cache when
  the network does not answer. The local copy of the lists is per account and cleared on sign-out.
  It stays readable on the device while signed in: protecting the device itself (lock screen) is
  still needed.

### Client IP

`X-Forwarded-For` is only read when the connection comes from `127.0.0.1` or an address in
`LISTES_TRUSTED_PROXIES`, and only its **last** value, the one added by the reverse proxy.
Otherwise a visitor could claim any IP and bypass per-IP blocking.

### Limits against exhaustion

A flaw or a stolen account must not be able to fill the host's disk or memory:

- database capped at **50 MB** (beyond: error 507, reads still work);
- 200 lists per account, 2,000 items per list, 500 characters per item, 80 per list name,
  requests of 16 KiB at most;
- 64 real-time streams in total, 4 per session;
- the same error message is logged at most once a minute;
- explicit timeouts on every HTTP stage.

### Container and deployment

- 16 MB **distroless** image: no shell, no package manager, nothing to exploit inside the image once
  in. The healthcheck is a subcommand of the binary.
- Runs as **uid 1000**, never root.
- The deployment should add: `read_only`, `cap_drop: ALL`, `no-new-privileges`, a single volume
  (`/data`), `pids_limit`, `ulimits nofile`, bounded logs, a port published on `127.0.0.1`.
- **No outgoing connections**: the app needs none, so block them all at the host level. Note that
  an iptables rule in the `DOCKER-USER` chain is not always enough: a VPN such as Tailscale puts its
  own chains before it and lets traffic to its network through. A **separate nftables table**
  (`prerouting` hook, new connections entering through the Docker network's interface) cannot be
  bypassed by any other table. Test it with a real destination on each network (Internet, LAN, VPN,
  host).

### Supply chain

- Only **two direct dependencies**: `golang.org/x/crypto` (Argon2id) and `modernc.org/sqlite`
  (pure-Go SQLite, no CGO). No npm, no front-end build step.
- Base images pinned by **digest**, GitHub Actions pinned by **SHA**.
- CI runs `govulncheck` on every push and **every night**. Dependabot proposes weekly updates of
  base images, Go dependencies and actions.
- The image is only published from `main` and `vX.Y.Z` tags, never from a pull request. Deploy a
  specific version (`:X.Y.Z`), never `:latest`.

## What the app does not protect

- **Lists are stored in clear text in the database.** Without end-to-end encryption, the host and
  its backups can read them. Do not put passwords or sensitive data in them.
- **No second factor**: a stolen password (reused elsewhere, phishing) gives access to the account
  until `listes user reset`. Hence the generated password, to be kept in a password manager.
- **The reverse proxy sees everything in clear text**: it terminates HTTPS.
